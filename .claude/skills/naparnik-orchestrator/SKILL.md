# Как работает оркестратор

1. **Сначала память проекта.** `knowledge/INDEX.md`, `knowledge/decisions.md`, `knowledge/lessons.md` (уроки прошлых сеансов), потом скилл `naparnik-knowledge`. Решения владельца главнее каталога.
2. **Цель одной строкой.** Что должно измениться в продукте в итоге. Исследование без применимого результата не запускать (правило владельца 09.11: «не ради воды»; даже малый прирост — брать в очередь A/B).
3. **Разрез работы.** Что делаю сам, что отдаю агентам. Агент получает: контекст продукта, красные линии, формат файла, один файл результата в `research/NN-…/`, запрет трогать git и другие файлы, запрет выдумывать числа.
4. **Бюджет поиска.** Веб-поиск общий на все параллельные агенты (около 200 запросов на ход). Каждому агенту писать потолок (≤ 40) или запускать по очереди. Непроверенное агент помечает, по памяти не дописывает.
5. **Приёмка.** Отчёт агента — не истина: проверить, что файл есть, строки посчитаны, непроверенное помечено. Незаконченный файл не коммитить, пока агент работает.
6. **В базу.** Новое — строкой в `knowledge/techniques.md` с ID в разделе этапа; то, что дополняет существующую строку, — ссылкой из неё («доп. NN/…»), а не дублем. Обновить чек-лист и счётчики в INDEX, строку в `research/README.md`, решение — в `decisions.md` с датой.
7. **Аудит сайта — глазами человека.** Поднять сайт, снять каждый экран на телефонной ширине, пройти путь целиком. Каждому приёму — конкретный экран и элемент, либо честное «негде» с причиной (экрана ещё нет / нарушает красную линию / противоречит решению владельца).
8. **Согласование.** Тексты владельца, тексты ASRS, цены, порядок экранов, всё спорное с решениями — только после его «да». Список на согласование — обычным структурированным текстом в чате, по экранам, с номерами приёмов.
9. **Код.** Один PR — одна тема. Тест, который падает на старой сборке. `pnpm check`, e2e; полную сборку подтверждает CI (в песочнице нет Google Fonts — локально только `next dev`).
10. **Мерж.** Только с разрешения владельца. Перед мержем: CI зелёный, конфликтов нет. Создание PR и мерж — разными командами. После мержа ветку начинать от свежего main (новой веткой, без force-push).
11. **Отчёт владельцу.** По-русски, обычным текстом, без воды: что сделано, что нашёл, что нужно от него. Скриншоты — файлами. Не выдавать незаконченное за готовое.
12. **Самообучение.** После каждой ошибки, отказа инструмента или замечания владельца — одна строка в `knowledge/lessons.md`: дата · что случилось · что делать впредь. В начале задачи эти уроки читать.
